# Как читать панель

[English](metrics.md) · [Русский](metrics.ru.md)

Формат строк: `now avg peak` (мс) — текущий кадр, среднее по окну (последние 120 кадров), пик с
последнего reset.

Бюджет кадра: `FrameMetrics.DEADLINE` (API 31+, столько система выделила кадру) или
`1000 / refreshRate`. На 60 Гц это 16.7 мс. Показан в заголовке.

На статичном экране показатели замирают — это норма, кадров нет.

## Управление

Панель перетаскивается пальцем. Тап по свёрнутой панели разворачивает. Long-press — freeze:
показания замирают для чтения, сбор продолжается. `×` — reset окна, сессии и пиков.

## CPU (main thread)

Работа UI-потока — тут живёт весь Compose и View-код приложения.

| Строка | Что покрывает | Растёт когда |
| --- | --- | --- |
| `input` | Обработка тач-событий и клавиш, включая все onClick/onTouch коллбэки | В обработчиках тяжёлая логика |
| `anim` | Расчёт текущих значений анимаций (`Animatable`, `animate*AsState`, `Transition`) | Много одновременных анимаций |
| `layout` | Measure + layout всех View и Composable | Глубокая иерархия, частые рекомпозиции, intrinsic measurements |
| `draw` | Запись draw-команд в DisplayList (`Canvas.draw*`, текст, фоны) | Много элементов на экране |

## RENDER (render thread)

Отдельный поток Android, который берёт DisplayList от UI-потока и превращает в GPU-инструкции.

| Строка | Что покрывает | Растёт когда |
| --- | --- | --- |
| `sync` | Синхронизация DisplayList из UI-потока + загрузка bitmap'ов как GPU-текстур | Большие или новые картинки |
| `command` | Преобразование draw-команд в OpenGL/Vulkan вызовы и отправка на GPU | Сложная иерархия View, много слоёв |
| `swap` | Ожидание пока GPU закончит предыдущий кадр + вывод на экран (`eglSwapBuffers`) | GPU перегружен |

## GPU

`gpu` — сколько GPU тратит на растеризацию кадра: шейдеры, отрисовка текстур, блендинг слоёв.
Доступно с Android 12+ (API 31), на старых устройствах `n/a`.

## Прочее

- `delay` — время от vsync-сигнала до реального начала работы над кадром. Растёт когда main thread
  занят чем-то другим: тяжёлый callback, IO, предыдущий кадр ещё не закончился
- `other` — остаток TOTAL, не разнесённый по фазам. В норме около нуля
- `TOTAL` — полное время кадра от vsync до завершения. Должно быть ≤ бюджета
- `over` — TOTAL минус бюджет: перерасход кадра, отрицательное значение = запас
- `pipe:cpu|rt|gpu` — стадия с наибольшим средним и её тайминги. Стадии работают параллельно, при
  устойчивой нагрузке fps упирается в неё, а не в TOTAL

## Подвал

- **FPS** — кадры, реально отрисованные за последнюю секунду. `idle` — кадров нет: статичный экран
  или замёрзший main thread
- **ui N/s** — сколько Choreographer-тиков обслужил main thread за секунду. Проседает ниже герцовки
  дисплея когда main thread занят; на LTPO-дисплеях плавает (60↔120)
- **jank** — кадр мимо системного дедлайна (`FrameMetrics.DEADLINE`, API 31+; до этого —
  `TOTAL > бюджет`)
- **win** — окно последних 120 кадров: доля jank, p95 и худший кадр
- **ses** — с последнего reset: перцентили p50/p95/p99, число кадров и время сбора (фон не
  считается), доля jank, `frz` — frozen frames (TOTAL > 700 мс, как в Play Vitals), `run` —
  максимальная серия jank-кадров подряд
- **drop** — сколько FrameMetrics-отчётов система дропнула, не успев доставить. Строка видна только
  когда > 0: avg/p95 недосэмплированы, метрикам верить с оглядкой
- **mem** — Java heap занято/лимит и native heap, `▲` — пики с reset. Ползёт вверх при навигации
  туда-сюда = утечка
- **gc** — количество и суммарное время сборок мусора с начала сбора. Растёт синхронно с jank =
  память давит на кадры
- **therm** — статус троттлинга PowerManager и headroom (ближе к 1.0 — жёсткий троттлинг). Скрыт
  пока статус недоступен

## Вердикт

Строка под заголовком:

- `✓ ok` — jank < 5%
- `⚠ <фаза> N ms` — фаза с наибольшим средним, включая `delay`; она же помечена `◀` в списке.
  Жёлтый — jank 5–20%, красный — ≥ 20%. В свёрнутом виде — бейдж `⚠<фаза>`

## Цвета

Строки метрик: зелёный — TOTAL в бюджете, серый — норма, красный — среднее по окну выше бюджета.

FPS (цель — герцовка дисплея): зелёный — ≥ 95% от цели, серый — ≥ 75%, красный — ниже. Серый `idle`
— кадры не рисуются.

Jank: < 5% норм, 5–20% подлагивает, ≥ 20% лагает.

## Как смотреть

Current прыгает — это ок, смотри на average.

1. **FPS против герцовки** — совпадают = плавно
2. **TOTAL average** — ниже бюджета = хорошо
3. **jank** — < 5% ок, > 20% плохо
4. **p95** — устойчивые просадки
5. **max** — разовые пики. Большой max при нормальном p95 = единичный хик, не проблема
6. **pipe** — какая стадия ограничивает fps под нагрузкой

## Как замерять экран

1. Открыть нужный экран
2. Reset (`×`)
3. Погонять 5–10 сек: скролл, переходы, анимации
4. Смотреть FPS против герцовки, TOTAL average, jank, p95
5. Если плохо — вердикт и `pipe` подскажут виновника

## Если что-то красное

| Строка | Что делать |
| --- | --- |
| `input` | Тяжёлая логика в обработчиках тачей/кликов. Вынести работу из onClick/onTouch |
| `anim` | Много или сложные анимации одновременно. Упростить, убрать лишние |
| `layout` | Рекомпозиции. `remember`, `derivedStateOf`, меньше инвалидаций |
| `draw` | Много элементов на экране. `LazyColumn`, убрать лишнее |
| `sync` | Тяжёлые картинки. Размеры bitmap, resize в загрузчике изображений |
| `command` | Слишком много draw-команд для render thread. Много слоёв, сложная иерархия |
| `swap` | GPU не освободился вовремя для вывода кадра. Обычно следствие тяжёлого `gpu` |
| `gpu` | GPU перегружен. Overdraw, blur, тени, alpha-слои, большие текстуры |
| `delay` | Main thread заблокирован. IO/network не на том потоке |
| `max` > 100 мс при нормальном p95 | Разовый хик, забить |
| `frz` > 0 | UI замерзал заметно для глаза. Искать длинную работу на main thread |
| `gc` растёт вместе с jank | Аллокации в горячем пути (композиция, скролл). Профилировать allocations |
| `mem` у лимита | Близко к OOM, искать утечку или тяжёлые кэши |

## Насколько числам можно верить

Панель рисуется в отдельном окне и в метрики измеряемого окна не попадает.

Искажают показания две вещи, и обе панель показывает сама: `drop` больше нуля означает, что система
выбросила отчёты не доставив, — avg и перцентили недосэмплированы; `therm` со статусом троттлинга
означает, что устройство сбросило частоты и тайминги несравнимы с холодным замером.
